# Bounded Nexus pilot: acceptance record

**Status (2026-11-26): local alpha rehearsed; live publication blocked on App scope; no public release.** The fork's consent is committed and read-only discovery works on GitHub. No Nexus comment was posted. See the [roadmap](roadmap.md) for the remaining release gates.

## Reproduce the local checks

**Clean installation and withdrawal (local observed):** [rehearsal and volunteer checklist](rehearsals/clean-install.md). The tested wheel installed in a new environment with a clean home and empty dependency cache using the public index. With only loopback available afterwards, OpenCode `/mcps` showed the connector; a separate SDK call discovered the fixture and was refused after revocation. Removing the project entry made the OpenCode list empty. Uninstall removed all three Nexus entry points and left the ledger intact (`PRAGMA integrity_check`: `ok`). No live model, human usability or GitHub publication was tested in this rehearsal.

Use Linux, Python 3.12+, the optional MCP extra, and an environment with pytest. To reproduce all acceptance cases, also have `ip`, `unshare`, `bwrap`, `sqlite3`, `curl`, OpenCode and Codex. The `uv --offline` steps require the build environment and wheels already in the local cache. Use a disposable Linux VM instead if unprivileged user namespaces are disabled. Run with synthetic inputs; no GitHub or model credentials are used.

```sh
# From the pilot checkout; use a new parent directory and a Python environment with setuptools >=77.
repo=$PWD
scratch=$(mktemp -d)
uv build --wheel --offline --no-build-isolation --python "$BUILD_PYTHON" --out-dir "$scratch"
uv venv --offline --python 3.12 "$scratch/venv"
uv pip install --offline --python "$scratch/venv/bin/python" \
  "$scratch/forgemesh_nexus-0.1.0a1-py3-none-any.whl[mcp]" pytest
sha256sum "$scratch"/*.whl
cd "$scratch"
unshare --user --map-root-user --net bash -eu -c '
  ip link set lo up
  export NEXUS_TEST_HOSTS=1 NEXUS_TEST_BWRAP=1
  ./venv/bin/python -m pytest --import-mode=importlib -q -rs -p no:cacheprovider "$1/tests"
  ./venv/bin/python -I -m forgemesh check-config "$1"
' bash "$repo"
```

Observed from outside the checkout: **200 passed in 35.51 s**, `OK: swarm 'nexus', 8 task(s)`. SHA-256 of the tested `forgemesh_nexus-0.1.0a1-py3-none-any.whl`: `522e52d4a49694faaf4751f7daaa295dfad8d8c416b574df23ac61520bd73151`. This identifies the tested build, not a signed release or promise of byte-identical builds. See the [operator rehearsal](operators.md#rehearse-without-github) for the installed console commands and the [participant guide](participants.md) for the MCP steps.

With the same installed wheel, the expanded suite (including the experimental trial gate and transport) returned **237 passed in 43.98 s** and `OK: swarm 'nexus', 8 task(s)`. The trial files are rehearsal artifacts outside the production wheel.

### OpenCode diagnostic limits

With a fresh home and project containing `mcp.servers.nexus`, `opencode api --standalone GET /api/config` saw the entry but `GET /api/mcp` returned an empty catalog and its connect route returned `MCP server not found: nexus`. The shared-service probe timed out waiting for startup. The standalone TUI is the proven path for connection and removal in this build; the automation initially misread ANSI repaint fragments rather than a failed connection. An earlier provider probe reported `provider.no-route` for a catalog `openai` override and a closed socket for a custom provider pointed at an unused port; a custom `@opencode/ai/providers/openai-compatible` provider pointed at a live loopback stub works. In this build `opencode run --standalone` reached the model without starting MCP. The TUI's `--prompt` also raced stdio initialization: the scripted provider's first tool list omitted `nexus_discover`, and OpenCode refused the call before listing the tool on the next request. For the interactive test, wait for both the terminal prompt and MCP catalog before sending input. Do not generalize these observations beyond v2.0.21.

## Live gate

A separate private ledger was initialized with `active_limit: 1` and `publication_limit: 1`, task `relinker-docs`, and distinct contributor, reviewer, maintainer and publisher owners. The fork's [consent commit](https://github.com/FRGMesh/anyps5/commit/89d8b1e42b29d21f8bec1bdf567edcd0e72a1ebf) permits one issue and two read paths, with no patch permission. GitHub compare reported `ahead`, one commit, only `.github/nexus.json` changed. Unauthenticated `propose` from the tested wheel against a fresh zero-capacity ledger returned #1 with that exact head, no skips and `truncated: false`; the ledger still had zero tasks and only its `initialized` event.

**Live blocker:** the private App `forgemesh-nexus-pilot-frgmesh` is installed with Issues write, Contents read and Metadata read, but GitHub's `GET /repos/FRGMesh/anyps5/installation` reported `repository_selection: all`. Its private key stays outside the ledger and harnesses. The owner must narrow the installation to `FRGMesh/anyps5`; no publisher token was minted and no Nexus comment was posted in this run. GitHub showed #1 open, unlocked, unassigned, with zero comments and an empty timeline. The tested `publish-github` command accepts a short-lived token via `NEXUS_GITHUB_TOKEN` only; tests cover missing credentials, extra fields and one POST over two calls.

**Antigravity (Gemini) attempt:** `agentapi` needs `ANTIGRAVITY_LS_ADDRESS` and `ANTIGRAVITY_CSRF_TOKEN`; it failed without them. After the app restarted, a second probe listed `discover` and `claim` under `nexus` (the conversation metadata still shows `launchedMcpServers: []`, so that field is not a reliable signal).

**Real agent patch (observed, 2026-11-26, rehearsal ledger):**

- **Setup:**
  - A fresh ledger (mode `0700`) with one `patch` task `build-doc`: issue 1, base `8cfc7e6`, paths `["docs/dev/BUILD.md"]`, `active_limit 1`.
  - A second MCP entry added to Antigravity's config was not loaded by the running app (`launchedMcpServers: []`; the agent said only `nexus` was available). The entry was removed, restoring the previous config.
  - Instead, the rehearsal ledger received the live `gemini` credential hash (audited as `operator_note`), and its participant API temporarily took port 8775. The already-launched `nexus` bridge therefore reached it without any token change. The live API was restarted on the live ledger right afterwards, and `discover` there returned `[]` again.
- **Agent:** Antigravity 2.35.2, conversation `acd13698-…`, model `gemini-4-hydrogen-tiered-high` ("Gemini 4 Hydrogen (High)", read from the conversation store), driven by the [participant prompt](participants.md), which now has the patch instruction. It:
  1. called `discover` and showed the issue, commit, kind and path;
  2. asked before claiming (`lease: 1`), then read only the issue and the two authorized raw files at the pinned commit;
  3. built the diff in a scratch copy, ran `git apply --check` itself, and showed it;
  4. submitted on approval ([diff](rehearsals/agent_patch.diff), digest `00aa5950…ac42`, 3,268 bytes).
- **Check:** `check-patch` against a depth-1 clone gave `{"ok": true, "files": ["docs/dev/BUILD.md"]}` in 0.91 s.
- **Independent review:** an OpenCode/Claude reviewer, a different owner, applied the diff at the base and recorded **`reject`**. The patch renames the relinker-only directory `build-relinker` to `build`, which the full build at line 98 also uses, despite line 19: "Use a separate build directory for the full build". It also leaves line 239 on `build-relinker`. `authorize` then returned `not_validated`.
- **Audit:** `claimed` and `submitted` by `gemini`, `checked ok`, `reviewed reject` by `claude`.
- **What this shows:** the sandbox check catches form and scope, not meaning, and the independent review caught a well-formed but harmful change. **What it does not show:** a non-technical participant (the operator typed the approvals), or a published patch.

**Codex against the live ledger (observed, 2026-11-26):** the user's real `~/.codex/config.toml` (Codex CLI 0.172.0) was backed up. A `nexus` entry was then appended, with `enabled_tools = ['discover']`, a separately enrolled contributor `codex` (owner `codex-gpt`), and the token read from a 0600 file by `/bin/sh -c`. Through `codex app-server` the following was observed:

1. `mcpServerStatus/list` listed only `discover`.
2. `discover` returned `{"repository": "frgmesh/anyps5", "tasks": []}`. The only task was already submitted by `gemini`, so a second contributor is not offered duplicate work.
3. A forced `submit` call was refused by Codex itself: `tool 'submit' is disabled for MCP server 'nexus'`.
4. After the maintainer ran `revoke`, `discover` returned `unauthorized`.
5. Restoring the backup made the config byte-identical to the original (`cmp`), and `codex mcp list` no longer showed `nexus`.

The audit gained only `enrolled` (codex) and `revoked` (mathis). A real Codex model turn could not run because the local ChatGPT login has expired (`refresh token has expired`); Codex therefore still has **no observed model-driven call**.

The "participant" answers in the Antigravity chat were typed by the operator agent, so this run does not measure a non-technical person's experience.

After the owner narrows the installation, verify its exact scope and mint a token restricted to the same repository. Recheck consent and the pinned revision, then use only the dedicated pilot ledger. Record the preflight, one bot-authored receipt verified by an independent read, the read-only retry/reconciliation outcome, a stale or withdrawn refusal, and final stop and credential removal. No cleanup by deletion is implied. Do not expose the loopback participant API remotely to run this gate. Judge whether to broaden the deployment only after actual client onboarding, maintainer feedback and the budget-matched comparison.
